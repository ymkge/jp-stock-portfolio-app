## 0.1 開発セキュリティ・個人情報保護規約 (Mandatory Security Policy) [最重要]

本プロジェクト（Antigravity CLI / AIエージェント / 開発者全員適用）におけるシークレットおよび個人情報の取り扱い規約。

### 1. API Key・シークレット情報のファイル非保持原則 [厳禁]
- `.json`, `.yaml`, `.txt` などのローカルディスク上のファイルに、API Key、アクセスキー、パスワード、その他認証シークレット情報を**保存・保持・記録する実装を一切行ってはならない**。
- GitHub などのオープンソース公開時に個人情報・認証情報が誤ってコミット・漏洩するリスクを根本的に排除する。

### 2. 環境変数およびメモリ内管理の徹底
- API Key やシークレット情報は、必ず **環境変数 (例: `GEMINI_API_KEY`)**、または **メモリ内 (Pythonオブジェクトのセッション変数等)** でのみ取り扱うこと。
- ファイルへ保存・永続化するコードの記述、および設定ファイルへのデフォルトキーの書き込みは固く禁止する。

### 3. 痕跡の即時消去 (Sanitization)
- ロード処理において過去の設定ファイル等に API Key や認証文字列が存在することを発見した場合、即座にメモリに読み込んだ上でファイルから当該項目を消去（ディスク上の痕跡消去）し、自動的にクリーンアップすること。

## 1. システムアーキテクチャ概要

本アプリは、Python (FastAPI) バックエンドと JavaScript (SPA) フロントエンドで構成される軽量なポートフォリオ管理ツールです。

### データフロー
1.  **取得**: `scraper.py` が Yahoo!ファイナンスからデータを取得。
2.  **加工**: `app.py` および `portfolio_manager.py` でスコア、損益、税金等を計算。
3.  **保存**:
    *   `portfolio.json`: 銘柄と保有情報のマスターデータ。
    *   `portfolio_history.db`: 
        *   `portfolio_history` テーブル: 月次の資産推移データ。
        *   `daily_analysis` テーブル: 日次の分析スナップショット（スコア、シグナル等）。
        *   `stock_price_history` テーブル: 日次の株価・出来高（時系列データ）。
        *   `portfolio_summary_history` テーブル: ポートフォリオ全体の合計値履歴。
        *   `split_alerts` テーブル: 株式分割・併合のアラートおよび対応履歴データ（`pending`, `applied`, `dismissed`）。
    *   `highlight_rules.json`: 各種判定基準（スコア、購入注目、ハイライト）およびシステム設定。
    *   `tax_config.json`: 資産タイプ別の税率設定。
    *   `security_companies.json`: 利用可能な証券会社のリスト。
4.  **表示**: フロントエンドが API からデータを取得し、`localStorage` にキャッシュしつつ表示。

## 2. 重要なロジック・アルゴリズム

### 2.1 設定管理 (`app.py`: `get_config`)

ハードコードを避け、`highlight_rules.json` から安全に設定を取得するためのヘルパー。

- **機能**: ドット区切りのパス指定、型強制、およびフォールバック（デフォルト値）をサポート。
- **活用**: スコア閾値、テクニカル指標の境界値、アイコン設定、クールダウン時間、市場確定時刻などに使用。

### 2.2 総合評価スコア (`app.py`: `calculate_score`) [強化]

最大16点（理論上の最大値はWフィボ加点を含む21点）の星印で表示される評価指標。

- **ファンダメンタルズ (黄色星)**: PER, PBR, ROE, 利回り, 連続増配、および**配当性向 (適正レンジ 20%〜60% を満たす場合のみ +1点)**。
- **トレンド・テクニカル (青色星)**: 移動平均乖離 (25日/75日), ゴールデンクロス, フィボナッチ (50-78.6%戻し), RCI26 (-80以下)。

### 2.3 購入注目フラグ (`app.py`: `calculate_buy_signal`) [強化]

国内株式を対象に、ファンダメンタルズとテクニカル指標を組み合わせて判定。

- **前提条件**: ファンダメンタルズスコア（PER, PBR, ROE, 利回り, 連続増配, 配当性向）が3点以上であること。
- **シグナルレベル**:
    - **レベル1 (🟡 注目)**: RSI(14)≦30, RCI(26)≦-80, またはフィボナッチ押し目(61.8-78.6%)のいずれかを満たす「売られすぎ」状態。
    - **レベル2 (🔥 チャンス)**: 以下のいずれかを満たす、トレンド転換または勢いの継続が確認された状態。
        - **中期ゴールデンクロス (25日/75日) [新規]**: 短期的なトレンドの好転を示す強力なイベント。
        - **25日線突破 [強化]**: 従来の5日線から、より信頼性の高い25日線へ基準を引き上げ、ノイズを排除。
        - **フィボナッチ・コンバージェンス (Wフィボ)**: 短期（3/6ヶ月）と長期（1年）の両方でフィボナッチ押し目圏内にある「強いサポート帯」への到達。
        - **RSI反転（前日比）**: 売られすぎからの回復を確認。
- **トレンド方向の明示 (Trend Orientation) [強化]**: 購入シグナルに対し、75日移動平均線との位置関係に基づきリスク度合いを分類。
    - **📈 順張り (Following)**: 株価が75日線の上にある状態。トレンドに沿った安全性の高い買い場。
    - **⚡ 逆張り (Contrarian)**: 株価が75日線の下にある状態。アイコンに雷（⚡）を付与し、推奨アクションを「短期リバウンド狙い・深追い厳禁」に自動切り替え。
- **長期調整の統合**: 75日線乖離率が-10%以下の銘柄には「＋長期調整」を付与し、推奨アクションを強気に上書きする。
- **ランク分けと視覚効果 (フロントエンド)**:
    - **🌈 虹色**: 💎ダイヤモンド ＋ チャンス(Lv2) ＋ 長期調整（最強）
    - **✨ 金色**: 💎ダイヤモンド ＋ チャンス(Lv2)
    - **🥈 銀色**: (チャンス ＋ 長期調整) または (💎 ＋ 注目 ＋ 長期調整)
    - **ダイヤモンド (💎)**: ファンダメンタルズスコアが4点以上の優良銘柄。
- **Wフィボ表示**: フィボナッチセルに紫色のバッジ（Wフィボ）を表示し、ツールチップでコンバージェンスの説明を追加。

### 2.4 シグナルの相反抑制と優先順位 (`app.py`: `reconcile_signals`) [強化]

ユーザーの混乱を防ぐため、購入と売却の両方のシグナルが同時に発生した場合の優先順位を明確に定義し、一つの有効なシグナルに絞り込む。

- **絶対リスク優先 (Level 4: 落ちるナイフ)**: 200日移動平均線を5%以上下回る「長期下降トレンド」にある銘柄は、ファンダメンタルズがどれだけ優秀であっても全ての購入シグナルを強制的に無効化（None）し、売却（リスク）シグナルのみを返す。
- **リスク優先 (Level 1, 2)**: 「ピークアウト(Lv2)」または「過熱気味(Lv1)」が発生している場合、短期的な下落転換リスクを最優先し、購入シグナルを抑制する。
- **購入・反転期待の優先 (Level 3: 長期調整) [変更]**: 75日線の下（長期調整）にあり、かつ今回の機能強化（GC等の購入チャンス）が発生している場合、従来の「売却優先」から**「購入優先」**に切り替え。下げすぎからのトレンド転換という最大のチャンスを逃さないように設計を変更。
- **実装**: `reconcile_signals` 関数にロジックを集約し、出力データの整合性を担保。


### 2.5 分析データの自己修復と仮想挿入 (app.py: _enrich_stock_data) [強化]

ロジック変更時やキャッシュ利用時でも、常に最新の計算結果を維持するための堅牢なデータ補完ロジック。

- **仮想挿入 (Virtual Insertion)**: 分析実行直前に、最新株価を履歴データの先頭に仮想的に追加してMAを計算。これにより、DBの更新タイミングに関わらず「今日クロスしたか」を正確に判定。
- **自己修復 (Self-Healing)**: 
  * **計算補完**: キャッシュから読み込まれた古い形式のデータ（MA_prev等が欠落）に対し、DBの価格履歴から動的に不足項目を再計算・補完します。
  * **再スクレイピングの防止 (防衛的補完) [新規]**: ロジック更新等に伴い新キー (`bps`, `payout_ratio` 等) が古いキャッシュデータに欠落している場合、キャッシュを破棄するのではなく、ロード時に自動で `N/A` 補完してキャッシュを延命します。これにより、銘柄数の多い本番環境での一斉再スクレイピング（403アクセス制限リスク）を防ぎます。
- **整合性担保**: 再計算されたデータに基づいて分析が更新された場合（`is_changed=True`）、自動的に新形式としてDBへ永続化される。
- **目的**: サイトへの再アクセス（スクレイピング）負荷を増やさず、ロジック変更を即座に全銘柄へ反映させる。

### 2.6 配当利回りのリカバリ (`scraper.py`: `JPStockScraper`) [強化]

Yahoo!ファイナンスから直接「配当利回り」が取得できない（`N/A` や `--`）場合、および1株配当が「未定（`---`）」の場合に、データ欠損を多層的に補完するロジック。

- **多層リカバリ構造**:
    1.  **直接計算**: 1株配当が取得できている場合、`(予想年間配当金 / 現在株価) * 100` で利回りを算出。
    2.  **詳細タブ補完 (新規)**: メインページの1株配当が未定（`---`）の場合、配当ページ（詳細タブ）の履歴データから「当期」または「来期」の最新予想値を抽出して補完。
- **年度の妥当性チェック**: 補完時に `current_year` ≦ $N$ ≦ `current_year + 1` の年度フィルタを適用することで、数年前の古い実績（ゾンビ配当）の誤用を防止。
- **目的**: 利回り欠損による総合スコアの低下や、購入注目フラグの判定漏れを防止し、情報の透明性を最大化する。

### 2.7 決算月の多層的抽出戦略 (`scraper.py`: `JPStockScraper`, `USStockScraper`)

Yahoo!ファイナンスの動的な仕様変更（JSONの構造変化やデータの文字列化）に対応するための堅牢な取得ロジック。

- **3段階のフォールバック**:
    1.  **JSON (指標データ)**: `referenceIndex` 内の PER/EPS 等に紐付く `date` から抽出。
    2.  **HTML (正規表現)**: ページ上の `DataListItem__date___6wH` クラス（見たままの日付表示）から直接抽出。
    3.  **メタデータ (配当基準日)**: 指標が取れない場合、`dpsPeriod`（配当権利月）を最終的な代替値として使用。
- **米国株式の決算月高精度パースとフォールバック (新規対応)**: [強化]
    - 以前は JSON 内の最初の `"updateDate"`（データ更新日の月）を誤検出して一律7月になっていた問題を解消。
    - **財務オブジェクト優先パース**: `eps`（一株利益）や `bps`（一株純資産）の更新日 `"updateDate":"YYYY/MM"`（実績決算期）から正規表現でピンポイントに決算月を抽出するロジックを実装。
    - **yfinance補完**: 上記で取得できない場合の最終セーフティとして、`yfinance` の `lastFiscalYearEnd` タイムスタンプから決算月を逆算する補完を導入。
- **目的**: 通信負荷を増やさず、サイトの見た方が変わらない限り確実に決算月を表示し続ける。

### 2.8 税金計算 (`portfolio_manager.py`: `calculate_holding_values`)

- `tax_config.json` を参照。
- `holding.account_type` が `non_taxable_accounts` (新NISA, 旧NISA等) に含まれない場合、`asset_type` に応じた税率を適用して「手取り配当」を算出。

### 2.9 ポートフォリオデータの排他制御とデータ整合性 (`portfolio_manager.py`: `portfolio_lock`) [新機能]

`portfolio.json` の読み書き時に発生しうる競合（ロストアップデート）やデータ破損を防止するための堅牢な排他制御ロジック。

- **二重ロック構造**:
    1. **スレッド間ロック**: `threading.RLock` を使用し、同一プロセス内の複数スレッドによる同時アクセスを制御。
    2. **プロセス間ロック**: `fcntl.flock` を使用し、ブラウザの複数タブやバックグラウンド処理（`sync_history.py` 等）との競合をOSレベルで防止。
- **再入可能 (Reentrant) 設計**: 同一スレッド内でのネストした呼び出し（例: `load_portfolio` 内で移行処理が走り `save_portfolio` が呼ばれる等）を許容し、デッドロックを防止。
- **トランザクションの保護**: 単なるファイル書き込みだけでなく、「読み込み → メモリ上での変更 → 書き込み」の一連のステップ（Read-Modify-Write）全体を `with portfolio_lock():` で包むことで、アトミックなデータ更新を保証。
- **例外安全性**: `try-finally` 構造（コンテキストマネージャ）により、処理中にエラーが発生した場合でも確実にロックが解放されることを担保。

### 2.10 履歴スナップショット (`history_manager.py`)

- **タイミング**: ユーザーが `/analysis` ページにアクセスし、API `get_portfolio_analysis` が呼ばれた際。
- **挙動**: 当月 (`YYYY-MM`) のデータが既にある場合は削除して再保存（月内最新化）。

### 2.11 スクレイピング安定化戦略 (`scraper.py`) [重要・強化]


大量リクエストによる Yahoo!ファイナンスのアクセス制限（403 Forbidden, 500エラー）を回避するための「お行儀の良いアクセス」ロジック。

- **接続維持 (Keep-Alive)**: `requests.Session` を導入。銘柄ごとの接続切断を避け、同一セッション内で通信を継続することでサーバー負荷を軽減する。
- **徹底した単一実行**: `concurrency_limit: 1`。複数の銘柄を同時に取得せず、1銘柄ずつ確実に処理する。
- **銘柄内待機 (Intra-stock delay) [強化]**: 国内株のように1銘柄で複数ページ（メイン・配当・履歴）にアクセスする場合、各アクセス間に **`1.2秒`** の待機を挿入。瞬間的な連打を物理的に防止する。
- **リトライ戦略 [新規]**: 通信失敗時のリトライ間隔を **`5.0秒`** に設定し、サーバー側の負荷状況に配慮したバックオフを実行。
- **偽装の最適化**: `Referer` ヘッダーの設定や `br` 圧縮の排除など、本物のブラウザに近い挙動を維持しつつ、遮断リスクを最小化する。

### 2.12 エラーハンドリングと判定不能シグナル (`app.py`, `scraper.py`) [重要]

データ取得の透明性と評価の信頼性を担保するための多層的なハンドリングロジック。

- **詳細エラーの伝播**: `scraper.py` の `BaseScraper` が HTTP ステータスコード（403, 500等）を保持し、`app.py` の `generate_error_message` がそれに基づき「15分待機」等の具体的ヒントを生成する。
- **即時中断 (Fast Interruption)**: 403 (Forbidden) を検知した場合、それ以上のリクエストがアクセス遮断を悪化させるのを防ぐため、サーキットブレーカーを即座に発動（更新を中断）させる。
- **評価信頼性 (`is_reliable`)**: PER, PBR, 配当利回りのいずれかが欠損（N/A）している場合、評価の信頼性が低いとみなし、星評価の横に警告アイコン（⚠️）とツールチップを表示する。
- **判定不能シグナル (🔘)**: `is_reliable` が False で、かつ他の指標による「注目（🟡）」や「チャンス（🔥 ）」の条件を満たさない場合、不当な低評価を避けるために「🔘 判定不能」バッジを付与する。
- **視覚的整合性の担保 (theme-unreliable)**: 背景と同化して視認性が損なわれないよう、`style.css` に `theme-unreliable` クラスを定義。ライトモードでは中立的なグレー（`#d1d8e0`）、ダークモードでは青みがかったグレー（`#4b6584`）と白い文字色を採用し、さらに「三層サンドイッチ構造」による低速シマーアニメーションを付与している。
- **フロントエンド同期**: `main.js` 和 `analysis.js` の描画ロジックを同期させ、ページを跨いでも一貫し た「判定不能」バッジが表示されるようにしている。

### 2.15 概算配当分布モデル (analysis.js: renderMonthlyDividendChart) [新機能]

- **目的**: サイトの仕様変更によるデグレリスクをゼロに抑えつつ、キャッシュフローの概算把握を可能にする。

### 2.23 AI投資方針適合診断とスマートキャッシュ管理 (llm_service.py, app.py, main.js) [新機能 #237 #241 #245]

ユーザー自身のオリジナル「投資方針プロンプト」に基づき、Gemini AIがポートフォリオおよび個別の銘柄適合度（Fit/Borderline/Avoid）を診断する機能と、そのアクセス最適化ロジック。

- **スマートキャッシュ (0.1秒化 & 429回避)**: 銘柄ごとの診断結果をメモリ内キャッシュ (`_cache`) で保持。有効期限 **12時間**、上限 **200銘柄 (LRU自動削除)**。2回目以降のアクセスは Gemini API を叩かず **0.1秒で即座に復元描画** し、Google API のレート制限（429）を物理回避。
- **複合キャッシュキーと自動無効化**: キャッシュキーは `code_assetType` だけでなく、選択モデル名 (`selected_model`) および `policy_prompt` の SHA256 ハッシュ値を検証。プロンプトやモデルが変更されると旧キャッシュは自動的に破棄される。また、`POST /api/investment-policy` 保存時には `llm_service_instance.clear_cache()` により全パージを実行。
- **UI表示バッジと強制再診断**: キャッシュ表示時はヘッダーに `⚡ キャッシュ表示 (HH:mm)` バッジを表示。フッターの `🔄 再診断 (最新データで診断)` ボタンを押すと `force: true` でリクエストを送信し、最新データで Gemini API を再実行・上書き更新する。
- **エラー非キャッシュ化**: 429レート制限や通信タイムアウトなどのエラーレスポンス (`error: True`) は**絶対にキャッシュせず**、次回アクセス時に自動で再実行・復旧できるように保護。
- **データ不一致の解消 (`yield` / `dividend_yield`)**: バックエンド側の配当利回りキー `yield` と `dividend_yield` の双方を多層フォールバック取得し、ROE/DOE 等の型安全フォーマット処理を行って Gemini API へ送信。高配当銘柄が「配当情報なし」と誤判定されるのを防止。

### 2.24 時系列配当推移 (履歴) 前月比ツールの動的算出 (analysis.js: renderHistoryCharts) [新機能 #242]

月次時系列の「配当推移 (履歴)」グラフにおいて、増減要因を視覚的に把握するための可視化ロジック。

- **時系列前月比コールバック (`afterLabel`)**: `dividend-history-chart` 用に Chart.js の `tooltip.callbacks.afterLabel` を拡張。直前の月 (`idx - 1`) のデータと比較し、`前月比: +44,684円 (+8.9%)` をツールチップ内に2行表示。
- **グラフ別の役割分離**:
    - **`dividend-history-chart` (配当推移 履歴)**: 時系列推移グラフであるため、前月比差分ツールチップを表示。
    - **`monthly-dividend-chart` (月別配当分布 予測)**: 1月〜12月の概算分布グラフであり、連続した前月比較は不要なため元の単行表示 (`予想受取額: X,XXX円`) を維持。
- **先頭月および0円時安全策**: 先頭月 (`idx === 0`) は `前月比: -`、前月配当0円時は `前月比: +X,XXX円 (新規計測)` と表示してゼロ除算（`NaN` / `Infinity`）を回避。
- **金額非表示モード連動**: `isAmountVisible === false` 時は `前月比: ***円` と自動マスク保護。
- **ブラウザキャッシュ対策**: `templates/analysis.html` 内の `<script src="/static/js/analysis.js?v=3.3"></script>` のバージョンアップにより、ブラウザの旧キャッシュ保持による反映漏れを防止。

- **目的**: 市場平均の変動に左右されず、自身の投資ポリシー（基準）に照らしてポートフォリオが健全な状態にあるかを即座に判断可能にする。

#### デグレ・リスクと対策 (Regression Risks & Mitigation)
1. **国内株式未保有時のエラー（ゼロ除算リスク）**:
   - **リスク**: 国内株式が登録されていない、あるいは国内株式の時価評価額が0の場合、加重平均計算時に分母が0になり `NaN` や `Infinity` が発生し、フロントエンドの描画処理が停止する。
   - **対策**: 分母（国内株式の時価総額合計）が0の場合は速やかに計算をスキップし、UI上に「国内株式のデータがありません（または登録されていません）」というプレースホルダメッセージを表示してエラーを隔離する。
2. **他アセットを含んだ分析指標（分散度・円グラフ）との整合性**:
   - **リスク**: 分散度（HHI指数・上位5占有率）や安全性スコア、円グラフは「ポートフォリオ全体（投資信託・米国株を含む）」を対象とする一方、DNA診断は「国内株のみ」を対象とするため、ユーザーが評価範囲を混同する。
   - **対策**: UIカードのヘッダータイトルに「国内株式ポートフォリオ体質 (DNA)」「ポートフォリオ特性 (Radar Chart) ※国内株式対象」などの表記を徹底し、評価のスコープを明示する。
3. **表示数値の急激な変化による混乱**:
   - **リスク**: 既存ユーザーがアップデートした際、これまで投資信託や米国株を含んでいた加重平均値から「国内株のみ」の数値へ切り替わるため、数値が急変してバグに見える。
   - **対策**: UIのタイトル改称によって「国内株式のみに対象を絞った」仕様変更であることを明示し、違和感を低減させる。

## 3. メンテナンス・トラブルシューティング

### 3.1 スクレイピング失敗への対応
Yahoo!ファイナンスの仕様変更により、特定の指標が `N/A` になることがあります。
- **調査**: `scraper.py` の `_make_request` で取得した HTML 内の `window.__PRELOADED_STATE__` を確認する。
- **対応**: `scraper.py` 内の各スクレイパークラス（`JPStockScraper`, `USStockScraper` 等）の解析パスを修正。

### 3.2 インテリジェント・キャッシュと市場イベント時刻 (`app.py`) [重要]

「安全な低速取得」と「開発・運用の高速化」を両立させるための多層キャッシュ戦略。

- **3層の引き当て**:
    1.  **メモリキャッシュ**: `cachetools.TTLCache` (1時間)。
    2.  **DBキャッシュ (鮮度判定)**: 以下の判定式に基づき、日付を問わずDB内のデータを採用。
        *   `データの更新日時 ≧ 最新の市場イベント時刻（開始 または 終了）`
        *   または、`現在時刻 - データの更新日時 < 1時間`
    3.  **スクレイピング**: 上記に該当しない場合のみ、並列制限（同時実行数1）と待機時間を伴って実行。
- **市場イベント時刻の算出**: `get_cache_threshold_time` 関数により、各市場の「直近の開始時刻（Open）」と「直近の終了時刻（Close）」のうち、より現在に近い方を算出。
    *   **ザラ場中**: 開始時刻（例: 09:00）が基準となるため、前日のデータは「古い」と判定されスクレイピングされる。
    *   **夜間・休日**: 終了時刻（例: 15:30）が基準となるため、大引け後の確定値がキャッシュとして有効に機能する。
- **目的**: ザラ場中のリアルタイム更新を保証しつつ、深夜・早朝や週末の不要なスクレイピングを完全に防ぎ、アクセス制限リスクを低減。
- **時間基準**: 内部処理は常に JST (Asia/Tokyo) に変換して行われ、サーバーのタイムゾーン設定に依存しない動作を保証。

### 3.3 データ整合性

- `portfolio.json` を手動編集する場合は、`id` (UUID) を壊さないように注意。
- `highlight_rules.json` に新しい設定を追加した場合は、`app.py` の `get_config` 呼び出し時のデフォルト値も更新することを推奨（堅牢性のため）。
- `load_portfolio` 時に自動マイグレーションが走るため、構造変更時は `_migrate_...` 関数 を追加して対応する。

## 4. デグレ防止ルール (Regression Prevention)

本アプリの安定性を維持するため、以下の開発ルールを厳守すること。

### 4.1 基本原則
- **Impact Analysis First**: 変更を開始する前に、影響を受ける既存の関数やモジュールを特定し、それらの現在の振る舞いを要約せよ。
- **Preserve Existing Logic**: 既存の正常な動作を維持することは、新機能の実装よりも優先度が高い。
- **No Deletion Policy**: 明示的な指示がない限り、既存のコード、エラーハンドリング、バリデーションロジックを削除・簡略化してはならない。
- **Dry-run Explanation**: 実装案を提示する際、「既存の〇〇機能への影響はないか」「どのように互換性を保ったか」を1行で説明せよ。

### 4.2 フロントエンドの障害隔離 (Error Isolation)
- **原則**: 1つの機能（グラフ、サマリー、テーブル等）の失敗が、ページ全体の描画を停止させてはならない。
- **対策**: 各描画関数（`renderSummary`, `renderCharts`, `renderDNAAndRisk`, `renderRadarChart` 等）は独立して動作し、内部でエラーが発生しても他の関数の実行を妨げないよう、適切な単位で `try-catch` を検討すること。

### 4.3 フロントエンド静的ファイルのキャッシュバスター運用ルール (Cache Busting Rules)
- **背景**: ブラウザは高速化のために JavaScript (`.js`) やスタイルシート (`.css`) をローカルに強くキャッシュします。ファイルに変更を加えた際、HTML側の読み込みタグに付与されているバージョンパラメータ（例: `?v=3.0`）を更新しないと、ブラウザは古いキャッシュファイルをロードし続け、修正が反映されません。
- **ルール**: フロントエンドの JS や CSS ファイルを修正してリリースまたは検証する際は、必ず呼び出し元の HTML ファイル（`templates/index.html` や `templates/analysis.html`）に記述されているインポートタグのクエリパラメータ（バージョン番号）を**インクリメント（引き上げ）**しなければならない。
  - 例: `static/js/analysis.js?v=3.0` を修正したら、HTML 側を `analysis.js?v=3.1` に変更する。

### 4.4 変更後の検証項目
- ページ全体の描画が完了するか（ローディングインジケーターが消えるか）。
- フィルタ適用時に数値が正しく更新されるか。
- 金額の目隠し機能が新しい項目にも適用されているか。

## 5. 拡張ガイド

### 2.24 排他的テーマ適用モデル (Single Theme Model) によるシグナル表示の完全制御 (style.css, main.js) [重要]

複数のCSSクラスが干渉し合うことによるデグレ（売却シグナルの色が水色になる、アニメーションが動かない等）を根絶するための設計思想。

- **設計思想**: 複数のクラスを重ね掛けしてCSSの詳細度に委ねるのではなく、JS側で状態（State）を評価し、最終的な「テーマ（唯一のCSSクラス）」を一つだけ決定して適用する。
- **実装内容**:
    - **骨格とテーマの分離**: CSSにおいて形状を定義する `signal-badge-base` と、背景色・アニメーションを定義する `theme-***` クラスを完全に分離。
    - **厳格な優先順位制御**: JSの `if-else` 分岐により、売却（リスク）やリッチ表示（虹・金・銀）の優先度を100%制御可能にした。
    - **売却優先の原則**: 優秀銘柄（💎）であっても、売却シグナル発生時は警告色（赤・オレンジ）を背景色として優先し、情報の誤認を防止。
- **目的**: 視認性の整合性を担保しつつ、CSSの肥大化や `!important` の乱用を防ぎ、将来的な改修時の安全性を最大化する。

### 2.25 UI/UX モダン化設計指針（Bento Grid & Skeleton UI） (style.css, analysis.js) [新基準]

プロフェッショナルな金融分析ツールとしての外観と操作性を両立させるための設計指針。

- **ベントー・グリッド (Bento Grid)**: 分析ページのサマリーエリアに採用。2列のグリッド配置により情報密度を最大化し、スクロールなしで主要指標を俯瞰可能にする。
- **スケルトンUI (Skeleton UI)**: データの取得中（スクレイピング中）にシマーエフェクト付きのプレースホルダーを表示。コンテンツの枠組みを維持することで、レイアウト・シフト（ガタつき）を防止し、体感速度を向上させる。
- **全画面ダークモード**: `localStorage` を使用したテーマ永続化と、Chart.js の動的な色追従（`getChartThemeColors`）を実装。
- **インタラクティブ要素の配色管理**: ボタン等の背景色にハードコードを避け、CSS変数 (`--button-bg-color`) を適用。ライト/ダーク各モードで最適なコントラストが自動的に保たれる設計を徹底。

### 2.26 金融分析に特化した視認性向上（Monospace & Sticky Header） [洗練]

大量の数値を正確に比較し、迷いなく操作するための細部へのこだわり。

- **等幅フォント (Monospace)**: 数値セル専用の `.numeric` クラスを定義。数字の幅を一定に揃えることで、上下行の桁数比較を直感的に可能にする（SFMono/Consolas等の等幅フォントセットを採用）。
- **スティッキー・ヘッダー (Sticky Header)**: テーブル上部に項目名を固定。スクロール時も常に現在のカラムを把握可能にする。
- **グラスモフィズム (Glassmorphism)**: 固定ヘッダーに半透明のぼかし（`backdrop-filter`）を適用。洗練された見た目と操作の連続性を確保。

### 2.27 三層サンドイッチ構造 (Three-layer Sandwich Structure) によるシグナル可視化 [新基準]

シグナルバッジのアニメーションにおいて、視認性、可読性、および他要素への非干渉を同時に成立させるための極めて堅牢なレイヤー設計。

- **設計思想**: 描画層を物理的に分離し、互いのプロパティ（背景色、透過度、文字の太さ）が干渉しない「サンドイッチ構造」を採用する。
- **レイヤー構成**:
    1. **最背面 (Base)**: `.signal-badge-base`。背景色と形状を定義。`z-index: 1` を付与し、内部の基準（スタッキングコンテキスト）を作成。
    2. **中間層 (Animation)**: `::after` 疑似要素. `z-index: 1` かつ背景より前面に配置. ここで光の移動（translateX）を実行. 
    3. **最前面 (Text)**: `.signal-badge-text`. `z-index: 2` を付与. 文字とアイコンを光のレイヤーから完全に独立させ、常にクッキリと表示させる. 
- **アニメーションの原則**: 透過度（Opacity）の変化はブラウザに間引かれやすいため、実績のある `transform: translateX()`（物理的な移動）を優先的に採用し、GPU描画を強制する。
- **安全性**: `overflow: hidden` を厳守し、アニメーションがバッジの枠外（隣のセルや固定ヘッダー）に 1px もはみ出さないように設計する。

### 2.28 テクニカル指標の算出根拠の透明化 (Technical Indicator Context) [新機能]

ユーザーが指標の信頼性を正しく判断できるよう、計算に使用したデータ期間（算出根拠）を可視化するロジック。

- **フィボナッチ算出期間 (`period`)**: 単なる「戻し率 (%)」だけでなく、直近何日間の高値・安値を対象とした計算かを `scraper.py` で算出し、フロントエンドへ伝播させるように拡張。
- **データ構造の拡張**: `fibonacci` オブジェクトに `period` (int), `high` (float), `low` (float) を含めることで、単一の数値ではなく「背景情報を持つオブジェクト」として定義。
- **UI表示 (Transparency)**: メインテーブルの数値にツールチップを実装。ホバー時に「算出期間: 125日」「直近高値: XXX円」といった詳細を表示することで、データの鮮度や算出範囲をユーザーが直感的に把握可能。
- **デグレ防止の徹底**: `app.py` のスコア算出ロジックは引き続き `retracement` プロパティのみを参照。メタデータの追加が既存の総合評価スコア（★）に影響を与えないよう、後方互換性を維持した設計を採用。

### 2.29 分析用ノートブックのデータ展開ロジック (portfolio_analysis.ipynb) [新基準]

データベース (`daily_stock_history`) に保存された JSON データをノートブックで詳細分析する際の、データ展開（フラット化）に関する設計指針。

- **キー名の完全一致**: DBには `change_percent` や `yield` といった最新のキー名で保存されている。`change_pct` などの旧名や想定外のキー名を使用しないよう、常に DB の `data_json` 実体を確認すること。
- **階層構造のフラット化**: 財務指標は `indicators` 等のネストではなく、JSON 直下にフラットに格納されている。抽出時は `data.get('per')` 等で直接取得する。
- **スコアの動的再計算**: `fundamental_score` や `technical_score` は DB に直接保存されていないため、`score_details` 内の個別フラグ（`per`, `pbr`, `roe`, `yield`, `consecutive_increase` 等）を抽出時に合計して算出する。
- **増配年数の派生計算**: `dividend_history`（年単位の辞書）から、最新から遡って増配・維持が続いている年数を動的に計算するロジックを実装し、分析項目を補完する。
- **目的**: Webアプリ上の計算結果とノートブック上の抽出結果の整合性を担保し、高度なバックテストや時系列分析を正確に行える環境を維持する。

### 2.30 算出仕様説明文のテーマ追従化 (Theme-aware Dividend Note) [改善]

月別配当分布グラフの下部に表示される「算出仕様」の説明文において、テーマ（ライト/ダーク）への完全な追従を実現したロジック。

- **背景**: 従来、説明文ボックス (`.dividend-spec-note`) の背景色が `#f8f9fa` に固定されていたため、ダークモード時に文字色が白に切り替わると「白背景に白文字」となり視認性が失われる問題があった。
- **対応**: 「UI/UX モダン化設計指針 (2.23)」を徹底し、ハードコードされた色指定を完全に排除。背景色を `var(--header-bg-color)`、メイン文字色を `var(--text-color)`、補足情報を `var(--text-muted)` にそれぞれ置き換えた。
- **目的**: グラフ本体（Chart.js）のテーマ追従と歩調を合わせ、分析ページ全体の視覚的一貫性とアクセシビリティを保証する。

### 2.31 新旧ハイブリッド抽出エンジン (Hybrid Extraction Engine) [新機軸]

Yahoo!ファイナンスの技術移行（Next.js化）の進捗が資産タイプごとに異なる状況（日本株：新、米国株・投信：旧）を、コード修正なしで吸収するための堅牢な抽出ロジック。

- **自動判別**: `BaseScraper` において `self.__next_f.push`（新）と `__PRELOADED_STATE__`（旧）の両方を探索。見つかった方の形式に合わせて動的にパース対象を切り替える。
- **後方互換性**: 米国株や投信が将来 Next.js へ移行しても、同一のハイブリッド基盤が自動的に新方式を選択するため、再度の取得不能リスクを最小化できる。
- **目的**: サイト側の不揃いな仕様変更に左右されず、全アセットの継続的な取得安定性を担保する。

### 2.32 スマート・スキップと重複検知同期エンジン (sync_history.py) [復旧・強化]

時系列データの欠落を解消しつつ、同期時間を最小化するためのインテリジェントな同期ロジック。

- **事前DB診断によるスマート・スキップ (Smart Skip)**: [強化] スクレイピング前にDBから銘柄ごとの「最新日」と「レコード数」を取得。ターゲット日を満たし、かつ1年分（250件）以上のデータがある場合は通信を完全にスキップする。
- **ダイナミック・ターゲット日算出**: 日本標準時(JST)の市場稼働時間を考慮。16:30（大引け確定）以降は「当日」、それ以前や週末は「直近の営業日」をターゲットとして自動算出。
- **欠落データの高精度補完**: `get_existing_dates` メソッドによりDB内の「穴」を正確に把握。1ページ目の取得で穴が埋まった場合は早期終了（Early Exit）し、不要なページ遷移を徹底的に排除。
- **株式分割時の最短補正フロー**: 同期対象となった銘柄のページ1において価格乖離（15%以上）を検知した場合、`apply_split_adjustment` によりDB内の全過去データを算出した比率で `UPDATE` 補正。直後に最新データで上書き保存を行い、即座に処理を終了する。
- **目的**: 403アクセス制限のリスクを最小化しつつ、長期指標（200日線、フィボナッチ等）の信頼性を常に最大化する。

### 2.33 時系列データの保存前バリデーションと信頼性管理 (Issue #4) [新基準]

時系列分析（移動平均、フィボナッチ等）の精度を担保するため、DB保存時にデータの妥当性を厳格に検証するロジック。

- **多層バリデーション (`validate_price_data`)**: 保存前に以下のチェックを実行し、異常値を検知。
    - **急激な価格乖離**: 前日比（または現在値）から ±50% を超える変化を異常値としてマーク。
    - **ノイズ行の排除**: 出来高の非整数チェックにより、Yahoo!の履歴に混入する配当支払行等を自動検知・排除。
    - **整合性担保**: 価格が0以下の不完全なデータの保存を拒否。
- **信頼性フラグ (`is_reliable`)**: `stock_price_history` テーブルにフラグを保持。バリデーションを通過しなかった（が致命的でない）データに `0` を付与し、将来の分析時に重み付けや警告表示を行える基盤を構築。
- **目的**: データのノイズによる分析シグナルの誤検知を未然に防ぎ、投資判断の質を向上させる。


### 2.34 フルワイド表示と統合フィルタ・ナビゲーション (Full-Width UI & Integrated Filter) [新機軸]

銘柄数が増加しても視認性を損なわず、分析ページと一貫した操作感を提供するための画面刷新ロジック。

- **サイドバーの廃止**: 17列に及ぶ国内株テーブルの横幅を最大限に活用するため、サイドバーを廃止。コンテナ幅を 100% (full-width) に拡張し、横スクロールの負担を軽減。
- **管理機能の上部集約 (Top Navigation Bar)**: 銘柄追加フォームと「最近の銘柄（ドロップダウン形式）」をヘッダー直下に集約。縦方向の占有スペースを最小限（1行分）に抑えつつ、直感的なアクセスを維持。
- **カードヘッダー型フィルタ (Integrated Table Controls)**: 分析ページと同様、テーブルを包含するカードのヘッダー部分に「タブ切替」「検索」「業種フィルタ」「シグナルフィルタ」「表示オプション」を横並びで配置。
- **シグナルドロップダウンの統合**: 従来チェックボックス形式だった買い場（✨）・格安（🎁）・リスク（🚫）の絞り込みを、排他的なドロップダウンに統合。UIの複雑さを解消し、最も重要な「現在の状態」に応じた銘柄抽出を容易にする。
- **目的**: 資産管理ツールとしての専門性を高め、情報密度の高さと操作の明快さを両立させる。

### 2.35 業種フィルタの動的生成と「その他」集約ロジック [新機能]

### 2.42 株式分割の自動検知・補正・履歴管理機能 (`sync_history.py`, `history_manager.py`, `app.py`, `main.js`) [新機能]

株式分割や併合発生時に過去の時系列株価データとユーザーの保有情報を一貫して自動補正し、過去の検知履歴を追跡・閲覧可能にするための統合機能。

- **2段階の分割検知**:
  - **リアルタイム簡易検知 (`app.py`)**: 画面読み込み時に直近DB株価と最新取得株価に30%以上の乖離がある場合、`potential_split` 警告フラグ（⚠️）をセットし手動同期を促進。
  - **確定的自動検知 (`sync_history.py`)**: Yahoo!ファイナンスから過去株価を同期する際、DBに保存済みの同日株価との比率の中央値を算出。15%以上の乖離があれば `round_split_ratio` で主要な分割比率に丸め込み、過去の株価・出来高を一括スケーリング補正。
- **データ管理と排他制御 (`history_manager.py`, `portfolio_manager.py`)**:
  - 検知されたアラートは `split_alerts` テーブルに保存。
  - 保有情報（取得単価 `/ ratio`、保有数量 `* ratio`）の補正更新時には `portfolio_lock()` による排他制御を適用。
  - ユーザーが「適用（`applied`）」または「無視（`dismissed`）」を選択してもレコードは物理削除されず、処理完了ステータスとしてDB内に永続化される。
- **過去履歴一覧表示 (`GET /api/split-history`, `main.js`)**:
  - フロントエンド画面右上に「✂️ 分割履歴」ボタンとモーダルを追加。
  - `/api/split-history` エンドポイント経由で過去に発生した全アラート履歴、検知日、分割比率、および適用ステータス（✅ 適用済み / 🚫 無視 / ⏳ 保留中）をテーブル形式で閲覧可能。
- **目的**: 株価の不自然な急落誤認やテクニカル指標の崩れを防ぎつつ、保有データの正確性と過去の分割対応の透明性を担保する。

## 7. 自動テスト・運用基準 (Issue #1 導入) [新基準]

本アプリの品質を維持するため、以下のテスト基準を遵守すること。

### 7.1 テスト実行のタイミング
- **コード変更時（必須）**: `app.py`, `scraper.py`, `portfolio_manager.py` 等の修正時は、必ず `python3 -m pytest tests/` を実行し、デグレがないことを確認せよ。
- **外部環境変化時**: Yahoo!ファイナンスの仕様変更等でデータ取得が不安定になった際、パースロジックの修正前後で実行せよ。

### 7.2 テスト追加の基準
- **新規判定ロジック**: スコア計算やシグナル判定に新しい条件（例：ゴールデンクロス、デッドクロス）を追加した際は、`tests/test_signals.py` に検証ケースを必ず追加せよ。
- **バグ修正時**: バグ発見時は、修正前に「失敗するテストケース」を作成し、修正後にそれがパスすることを確認する手順（TDD的アプローチ）を推奨する。

### 7.3 スクレイピングテストの原則
- **モック（オフライン）テスト**: `scraper.py` のテストは実サイトへの通信を行わず、保存されたHTML/JSONデータ（モック）を用いてパース処理の正当性を検証すること。

### 7.4 合格基準
- **全件パス (All Green)**: 1件でも失敗がある状態での運用・デプロイは禁止。
- **網羅性**: 判定ロジックの主要な分岐（正常系・境界値・異常系）をテストデータで網羅すること。
